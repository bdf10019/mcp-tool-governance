# 去內容備份與隔離還原契約

## 目的

此契約用於保存產品結構、設定版本與業務關係證據，同時避免備份成為密碼、私人內容或可執行核准權威的第二份來源。它不是完整災難復原格式。

## 備份封裝

最外層只有：

- `manifest`：格式、備份 ID、時間、來源環境種類／指紋、schema、payload SHA、列數、包含／排除清單及 `authority_included=false`。
- `payload`：固定白名單投影。

檔案名稱由後端產生，保存在目前資料庫的環境根 `backups` 子目錄。呼叫端不能提交路徑。檔案先寫入同目錄臨時檔、flush／fsync，再以原子 replace 完成；DB 只登錄完成檔。

## Payload 白名單

1. schema 版本與 migration ledger metadata。
2. Profile 設定快照、版本、來源狀態、policy 與 snapshot SHA。
3. 合成 seed 版本與 Profile source SHA。
4. 去識別帳號數、啟用數、角色及 scope 統計。
5. 提案、核准、執行、工單的雜湊參照、狀態、版本、Profile／設備、時間及證據種類。
6. 依 event type／status／tool 聚合且不含 summary 的 Trace 統計。

## 永久排除

- username、password hash、salt。
- session cookie/hash、CSRF、auth context、Token、secret。
- 原始工具 arguments／result、Trace summary。
- proposal parameters、issue summary、maintenance window、risk summary。
- reviewer ID、審核理由、完整工單內容。
- idempotency key、request hash、outbox payload。
- 任何外部 URL、任意程式、SQL、使用者指定路徑。

## 驗證與拒絕

下載與還原前都重新確認：DB 登錄狀態、允許目錄、一般檔案、非 symlink、檔案 SHA。還原另驗證 envelope 欄位恰為 manifest／payload、格式、備份 ID、schema、`authority_included=false` 與 payload SHA。任一項不符即拒絕。

## 還原模型

還原建立全新 UUID 路徑及專用 SQLite，只含：

- `restore_meta`
- `restored_profile_candidates`
- `restored_business_records`

active Profile 轉為 `pending_validation_readonly`，業務關係轉為 `restored_readonly`。不建立 users、sessions、auth contexts、approvals、executions、orders、outbox 或 MCP 工作入口。還原完成後將 DB 設為唯讀，並保存收據；應用層安全不依賴單一檔案權限。

每個來源環境指紋使用不同還原 bucket。`automated_test` 的備份／還原只寫在該次測試 DB 暫存根，避免測試證據進入產品 `state`。收據另附 canonical SHA-256；讀取時不符即忽略，不把遭竄改的零權威數字顯示為證據。

## 收據最低欄位

- restore／backup ID、建立時間。
- 目標環境種類、指紋與邏輯相對路徑。
- 來源邏輯內容 SHA 未改變。
- 待驗證 Profile 候選數、唯讀業務關係數。
- sessions、auth contexts、active approvals、auto replay、MCP calls 均為 0。
